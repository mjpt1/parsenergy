# پاسخ به درخواست اتصال دستیار Vida به سامانهٔ pars-tida.ir

سرکار خانم مشفق، با سلام و احترام

بررسی فنی انجام شد. خلاصه این است که **سامانه از قبل API دارد**، احراز هویت و
کنترل دسترسی سطح‌رکورد روی آن اعمال می‌شود و مستندات OpenAPI هم تولید می‌کند.
برای اتصال Vida نیازی به بازنویسی نیست؛ فقط یک لایهٔ فقط‌خواندنی و محدودشده
روی همین API اضافه می‌شود. جزئیات در ادامه.

---

## ۱. وضعیت API فعلی

| مورد | وضعیت |
|---|---|
| چارچوب | Django REST Framework روی Django 5.0.8 / Python 3.11 |
| آدرس پایه | `https://pars-tida.ir/api/` |
| مستندات OpenAPI 3 | `/api/schema/` (JSON) |
| کنسول تعاملی Swagger | `/api/docs/` |
| احراز هویت | Token (هدر `Authorization: Token <...>`) و Session |
| صفحه‌بندی | `PageNumberPagination`، پیش‌فرض ۲۵ رکورد در صفحه |
| فیلتر و جست‌وجو | `django-filter` روی مسیرها فعال است |
| محدودیت نرخ | کاربر احرازهویت‌شده ۶۰۰ درخواست در دقیقه، ناشناس ۶۰ |
| فرمت | JSON |

مسیرهای موجود، متناظر با فهرست مورد نیاز شما:

- **درخواست‌های فنی** — `/api/requests/`
- **پیشنهادهای قیمت** — `/api/request-offers/`
- **قراردادها** — `/api/request-contracts/`
- **پرداخت‌ها** — `/api/request-payments/`
- **نیروگاه‌ها** — `/api/plants/`
- **اینورترها / ترانسفورمرها / گیت‌وی‌ها** — `/api/inverters/`، `/api/transformers/`، `/api/gateways/`
- **داده‌های پایش و تولید** — `/api/telemetry/`، `/api/environmental/`،
  `/api/realtime-measurements/`، `/api/historical-measurements/`
- **هشدارها و خطاها** — `/api/alert-events/`، `/api/alert-rules/`
- **اعلان‌ها** — `/api/notifications/`

پاسخ به این نکتهٔ شما که «مسیرهای درخواست‌ها، پیشنهادها، تیکت‌ها و نیروگاه‌ها
پاسخ HTML دارند، حتی با fetch»: آن مسیرها صفحات پنل هستند (`/requests/…`)
و عمداً HTML برمی‌گردانند. API مستقل زیر `/api/` قرار دارد و خروجی JSON می‌دهد.
فایل HAR شما احتمالاً فقط ترافیک پنل را ثبت کرده است.

## ۲. احراز هویت و کنترل دسترسی

کنترل دسترسی **در سمت سرور و روی تک‌تک رکوردها** اعمال می‌شود، نه در لایهٔ نمایش.
هر ViewSet مجموعهٔ رکوردهای خود را بر اساس کاربر درخواست‌دهنده محدود می‌کند؛
برای مثال نیروگاه‌ها از `plant_scope_for_user` و درخواست‌ها از
`requests_for_user` عبور می‌کنند. رکوردی که برای آن کاربر مجاز نیست، اصلاً در
نتیجه ظاهر نمی‌شود — نه اینکه ظاهر شود و پنهان بماند.

حذف فیلدهای حساس برای نقش فنی هم **از قبل پیاده‌سازی شده** است. در سریالایزر
درخواست‌ها، وقتی کاربر از نوع فنی باشد، فیلدهای `full_name`، `mobile` و `user`
پیش از ارسال از پاسخ حذف می‌شوند. یعنی همان سیاستی که در پنل اعمال می‌شود، در
خروجی API هم برقرار است.

**دربارهٔ OAuth 2.0:** در حال حاضر پشتیبانی نمی‌شود. پیشنهاد ما به‌جای آن
**توکن اختصاصی هر کاربر** است: هر کاربر از پنل خودش یک توکن برای Vida صادر
می‌کند، Vida دقیقاً در محدودهٔ مجوزهای همان کاربر کار می‌کند، و کاربر هر زمان
بخواهد توکن را ابطال می‌کند. این دقیقاً همان مدل امنیتی OAuth را می‌دهد بدون
هزینهٔ پیاده‌سازی و نگهداری یک Authorization Server. اگر OAuth برای شما الزام
قطعی است، قابل افزودن است ولی زمان و هزینهٔ جداگانه دارد.

## ۳. آنچه باید اضافه شود

API فعلی برای مصرف داخلی پنل ساخته شده و دو فاصله تا نیاز شما دارد:

۱. **فقط‌خواندنی نیست.** مسیرها از نوع `ModelViewSet` هستند، یعنی علاوه بر
   `GET` متدهای `POST`/`PUT`/`PATCH`/`DELETE` را هم می‌پذیرند. شرط شما این
   است که هیچ عملیات نوشتنی ممکن نباشد. راه‌حل ما بستن این متدها در سطح توکن
   است — نه اتکا به اینکه Vida آن‌ها را صدا نزند.

۲. **تیکت‌ها و پیوست‌ها مسیر API ندارند.** تیکت‌های فنی و فایل‌های پیوست
   (قبض برق، دیتاشیت، گزارش) فعلاً فقط از پنل در دسترس‌اند.

پیشنهاد ما **مسیر اول** شماست: API فقط‌خواندنی و احرازهویت‌شده در سمت ما، و
واسط MCP در سمت Vida. دلیل: کنترل دسترسی همین حالا در سمت سرور وجود دارد و
فقط باید محدود شود؛ ساختن یک سرویس MCP جداگانه روی زیرساخت سایت یک مؤلفهٔ
اجرایی تازه اضافه می‌کند که باید مستقل نگهداری، به‌روزرسانی و پایش شود، بدون
آنکه امنیت بهتری بدهد. سرویس MCP روی میزبانی اشتراکی cPanel محدودیت اجرایی
هم دارد.

**تقسیم کار پیشنهادی**

| سمت پارس تیدا | سمت Vida |
|---|---|
| توکن فقط‌خواندنی با قابلیت ابطال | پیاده‌سازی واسط MCP |
| بستن متدهای نوشتن روی آن توکن | نگاشت ابزارها به مسیرهای API |
| مسیرهای API تیکت‌ها و پیوست‌ها | مدیریت توکن در سمت خود |
| فیلتر «تغییرکرده از تاریخ» (`modified_since`) | — |
| ثبت درخواست‌های Vida در سوابق سامانه | — |
| حساب آزمایشی با دادهٔ غیرواقعی | — |

## ۴. اطلاعات فنی زیرساخت

- **بک‌اند:** Django 5.0.8، Python 3.11، Django REST Framework
- **پایگاه داده:** MariaDB
- **میزبانی:** cPanel با LiteSpeed و Phusion Passenger؛ ترافیک ورودی فقط روی
  ۴۴۳ و HTTPS اجباری است (ریدایرکت ۳۰۱ از HTTP، به‌همراه HSTS)
- **افزودن مسیر API یا زیردامنه:** هر دو امکان‌پذیر است
- **قالب تاریخ:** ISO 8601 در خروجی API؛ نمایش پنل شمسی است
- **منطقهٔ زمانی:** `Asia/Tehran`
- **واحدها:** توان بر حسب کیلووات (kW)، انرژی بر حسب کیلووات‌ساعت (kWh)، دما
  بر حسب درجهٔ سلسیوس، مبالغ بر حسب **تومان**
- **شناسهٔ یکتا:** کلید عددی `id` برای هر رکورد
- **داده‌های پایش:** از طریق مسیر دریافت اندازه‌گیری‌ها و اتصال اینورترها وارد
  می‌شود؛ تناوب به تجهیزات نصب‌شده بستگی دارد و در حال حاضر نیروگاه فعالِ
  متصل نداریم، بنابراین برای مرحلهٔ آزمایش دادهٔ نمونه تولید خواهیم کرد

## ۵. معیار تحویل مرحلهٔ اول

با معیارهای پیشنهادی شما موافقیم و برای هر پنج مورد تست خواهیم داشت:

- دریافت فهرست و جزئیات اطلاعات مجاز — ✅ قابل پوشش
- یکسان بودن دادهٔ API با آنچه همان کاربر در پنل می‌بیند — ✅ از یک منبع می‌آیند
- مسدود شدن رکوردهای غیرمجاز در سمت سرور — ✅ همین حالا برقرار است
- ناممکن بودن هر عملیات نوشتن — نیاز به کار جدید (بند ۳)
- عملکرد درست قطع و ابطال دسترسی — نیاز به کار جدید (بند ۳)

## ۶. گام بعدی

پیشنهاد می‌کنیم ابتدا تیم Vida مستندات `/api/schema/` را بررسی کند تا مشخص
شود کدام مسیرها نیاز Vida را پوشش می‌دهند و چه چیزی کم است. پس از آن فهرست
نهایی مسیرها و برآورد زمان و هزینه را ارائه می‌کنیم.

برای تحویل توکن آزمایشی، لطفاً یک کانال امن جداگانه هماهنگ کنید؛ مطابق توصیهٔ
خودتان، توکن را در پیام معمولی ارسال نخواهیم کرد.
